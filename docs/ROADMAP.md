# Roadmap

Work ships in tested increments that are deployed to a real network as they land.

| Step | Theme | State |
|---|---|---|
| 1 | Docker testbed, preflight, Tailscale migration | done |
| 2 | **Core:** DNS engine, self-healing upstreams, guarded lists, portal, Private Relay policy | done, live on the NAS |
| 3 | **History, map and stream:** encrypted searchable history, geolocated destinations, live event stream, automatic home | done, live on the NAS |
| 4 | **Policy:** a catalog of lists, apps and categories, custom lists, scopes (network, group, device) | done, live on the NAS |
| 5 | **Upstreams:** plain, DoT and DoH with bootstrap, presets, test before adding | done, live on the NAS |
| 6 | **Devices:** registry, names from mDNS and the neighbor table, vendors, groups, search, bulk edit, automatic classification (DNS/vendor/ASN), wandering mode (unfiltered + watched) | done, live on the NAS |
| 7 | **Portal:** the globe HUD (arcs weighted by volume, replay, click to control) and the Devices/Blocking/Upstreams/History management screens | done, live on the NAS |
| 8 | **Device quarantine:** new devices land in a reserved group with their own rules until moved; LAN isolation is out of Shepherd's reach today (see the Watch mode note below) | done, live on the NAS |
| 9 | **Alarms:** engine with dedupe, severity, mute and snooze, batch actions, Web Push and ntfy fallback | engine, `cmd/shepherd` wiring, portal API and an Alarms tab (list, filters, bulk actions, mute rules) done, live via ntfy; Web Push deferred until the portal has HTTPS (see docs/ALARMS.md) |
| 10 | **Passive ARP:** a read-only monitor that learns MAC addresses and raises spoofing/exposure alarms | built and wired into `cmd/shepherd`; its `gateway-mac-changed` event is now consumed by Watch mode (which re-reads the kernel's neighbour table rather than trusting the event), and the alarm-engine wiring for the other event types is still open |
| 11 | **Watch mode (ARP interception):** one-sided relay of each device's outbound traffic, with exclusion, health-checked fail-open, a kill switch, per-device switches and an in-kernel XDP relay | **done, live on the NAS, on by default.** The throughput ceiling that held this back for months was root-caused and fixed on 2026-10-30 (the relay used the device's own source MAC, which made the switch's MAC table flap and dropped the device's *inbound* traffic — see [INTERCEPT.md](INTERCEPT.md)); with that fix a steered phone held full gigabit Wi-Fi with no perceivable slowdown, relaying 1.6 Gbit/s through the userspace relay and 1.77 Gbit/s through the new in-kernel XDP relay. With the maintainer's explicit go-ahead it is now wired into `cmd/shepherd` (`internal/watch`) and the portal: on by default, every eligible device steered, a Watch screen with live relayed throughput and a kill switch that persists across restarts, a three-way switch per device, and automatic exclusion of the gateway, Shepherd itself, excluded devices and all network/smart-home/Thread/Matter gear. IPv6 steering (unicast Neighbor Advertisements, never RAs) is built and wired behind `watch.ipv6`, **off by default** and idle on a network without a global IPv6 route — see [IPV6-WATCH.md](IPV6-WATCH.md). Still outbound-only by construction, and still blocks nothing: per-device pause, bandwidth limits and IDS need the return path, which means two-sided interception or Gateway mode. See [WATCH.md](WATCH.md) and [WATCH-MODE-COMPARISON.md](WATCH-MODE-COMPARISON.md). |
| 12 | **Router importers:** eero (unofficial API, unverified against a live account) and CSV, to bring in existing device names and groups | built and wired into the portal |
| 13 | **Scheduled access and allowlist mode:** time windows on a policy rule or switch at network, group or device scope (block or allow a category, app or list only during chosen hours/days); and an allowlist mode, settable at the same three scopes, that inverts the default to block everything except what is explicitly allowed, instead of today's block-list default | built and wired into `internal/dnsengine` and the portal (docs/POLICY.md) |
| 14 | **Geo-IP blocking:** block (or alert on) connections to specific countries, at network, group or device scope, reusing the GeoIP database already used for the globe HUD | in progress |
| 15 | **Network health history:** ping/latency, jitter, packet loss, bufferbloat, reachability and traceroute, run on an interval and kept over months so reliability trends are visible, not just this instant | latency/jitter/loss/reachability and a bounded bufferbloat check built and wired into `cmd/shepherd`, the alarm engine (`alarms.TypeNetworkDegraded`) and the portal (docs/NETHEALTH.md), with raw/hourly/daily rollup so history grows over months without growing without bound; latency is timed as an unprivileged TCP connect to port 53 rather than ICMP echo (no `CAP_NET_RAW`) and verified live against the real internet during development (see docs/NETHEALTH.md's "What is verified" section); both the probe and bufferbloat default off, unlike portscan/vulnscan, since this reaches fixed public internet addresses rather than only the owner's own LAN; traceroute is deferred, the same way step 16 deferred router port-forwarding discovery, for lack of a safe, verified raw-socket implementation |
| 16 | **Ports and exposure:** scheduled scans, per-device open ports, change alarms | built and wired into `cmd/shepherd` and the portal (docs/PORTSCAN.md); router port-forwarding discovery is not built — there is no reliable, generic router API for it |
| 17 | **Vulnerability scanning:** a curated, built-in signature layer on top of step 16's open-port findings — banner/protocol probes matched against named, concrete vulnerabilities (old SSH/OpenSSH, unencrypted/anonymous FTP, outdated web server banners, unauthenticated Docker API over plain HTTP and TLS, SMBv1, outdated TLS versions/ciphers, expired certificates, UPnP exposure), not just "port N is open" | built and wired into `cmd/shepherd`, the alarm engine and the portal (docs/VULNSCAN.md); still no external CVE API or OS-level vulnerability database, no SSLv3 detection (Go's TLS stack dropped it), no SSDP/IGD-based UPnP discovery (a different, lower-level feature), no threat feeds (that's step 23) |
| 18 | **Access:** reverse proxy, wildcard certificates on Cloudflare DNS, private service names, Cloudflare Tunnel; migrating off the current reverse-proxy manager | `[tls]` gives the portal itself a real certificate for its own hostname via ACME DNS-01 against Cloudflare (docs/TLS.md). **Reverse proxy built** (`[reverseproxy]`, docs/REVERSEPROXY.md): HTTPS and WebSocket proxying of other services by hostname behind one wildcard certificate, hosts managed in the portal's Proxy tab, off by default and listening on `:8443` until the owner moves it; WebSocket upgrades proven end to end in tests; no per-host access control, HTTP-to-HTTPS redirect or import from the existing manager yet. Not yet run against real traffic or a real wildcard issuance: the live cutover off the existing manager is a supervised next step following that doc's checklist. Private service names and Cloudflare Tunnel remain planned |
| 19 | **Portal locking:** demo data until unlocked, idle auto-lock (configurable, including never), PIN bound to a trusted browser | built; not yet deployed. Passkeys still wait on step 18 (HTTPS) |
| 20 | **Inbound protection:** logging, rate limits and blocking at the proxy and tunnel, exposure alarms, host-level inbound tracking | planned |
| 21 | **Mesh:** dataset sync, active-active DNS, standbys | planned |
| 22 | **Self-maintenance:** signed self-update with rollback, retention budgets, digests | planned |
| 23 | **Threat feeds and local AI** | planned |
| 24 | **Packaging:** installers, setup wizard, release channels — including a Raspberry Pi / low-power-hardware path: Shepherd already cross-compiles to `linux/arm64` in CI, so DNS-only protection and passive ARP already run on cheap hardware people already own; Watch mode's software relay is the part that needs real headroom, not the baseline. **The stated goal here is not "easier for techies" — it's that a non-technical person should never need a terminal or a text editor at all.** Today, first setup means hand-editing `shepherd.toml` and running a binary by hand; that's acceptable for the current development phase but is explicitly *not* the bar for a real release. The portal itself should walk a new owner through setup (upstream choice, data directory, initial blocklist, locking a PIN) and keep itself running afterward (updates, retention, housekeeping) with no config file ever touched by hand — self-update (step 22) and the setup wizard here are two halves of the same promise: install it, answer a few questions in a browser, and it just works, indefinitely, for someone who has never heard of DNS. **Target hardware is deliberately broad, not just a NAS or a dedicated box**: a Raspberry Pi, a spare gaming PC, a Mac mini someone already owns — anything idle on the network. Shepherd already cross-compiles with no CGO to Linux, macOS and Windows (see the Wave 2 entry at the top of CHANGELOG.md); what's missing for each isn't the binary, it's a real installer (an .exe/.pkg/.deb or similar, not "download a binary and figure out how to run it as a service") so "easy setup" means the same thing on every platform. | planned |

## Stated future direction: Shepherd as a dual-NIC router

The maintainer wants to eventually run Shepherd as the actual router (a "Gateway" profile), on
hardware with two 10 Gb NICs, demoting the current Wi-Fi router to a bridge/access-point role. This is
real intent, not a research idea, but it is a large undertaking that only makes sense once Watch mode
is proven reliable, and it changes Shepherd's risk profile fundamentally (a router outage is a full
outage). See [DESIGN.md](DESIGN.md#gateway-shepherd-as-a-dual-nic-router-future-stated-goal). Not scheduled.

Other research items: passive IPv6 observation, NAT state sync for seamless failover, and full
two-sided (peer) ARP isolation for quarantine/LAN-isolation beyond what one-sided Watch mode can
offer. In-path IPv6 is no longer research: unicast-NA steering is built and wired (off by default,
[IPV6-WATCH.md](IPV6-WATCH.md)), though it has never run against a live global-IPv6 network — the
maintainer's own LAN is ULA-only, so it idles there by design.
