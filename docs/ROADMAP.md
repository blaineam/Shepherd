| 3 | **History, map and stream:** encrypted searchable history, geolocated destinations, live event stream, automatic home | done, live on the NAS |
| 4 | **Policy:** a catalog of lists, apps and categories, custom lists, scopes (network, group, device) | done, live on the NAS |

| 9 | **Alarms:** engine with dedupe, severity, mute and snooze, batch actions, Web Push and ntfy fallback | done: engine, `cmd/shepherd` wiring, portal API and an Alarms tab (list, filters, bulk actions, mute rules), ntfy delivery, and since 2026-11-01 Web Push end to end (VAPID keys, subscription endpoints, a service worker, a Notifications tab with "send a test"); not yet exercised against a real push service from a real browser (docs/ALARMS.md) |
| 10 | **Passive ARP:** a read-only monitor that learns MAC addresses and raises spoofing/exposure alarms | done: built and wired into `cmd/shepherd`, every event type mapped to an alarm or deliberately to none (docs/ARP.md, "As alarms"), and `gateway-mac-changed` also tells Watch mode to re-read the kernel's neighbour table |
| 11 | **Watch mode (ARP interception):** one-sided relay of each device's outbound traffic | **Opt-in, off by default; reinstated 2026-11-01 (evening) after being retired that morning.** Outbound-only by construction, so downloads are estimated from TCP acknowledgements ([TRAFFIC.md](TRAFFIC.md)). The "loops" behind the retirement were uploads: the sampled frames all carried IP identification 0, as macOS sends don't-fragment packets, and the verdict counted identification fields. The loop brake now needs frames actually coming round (duplicates, returned output, or identical samples) or 300,000 pkt/s before it stops anything; the real echo -- the segment handing a frame back once, tens of microseconds later -- is dropped by both relays; a dual-homed forwarding host runs by default; Ethernet is preferred over Wi-Fi. A device with connections already open can keep sending them to the real router, so per-device numbers remain partial. [WATCH.md](WATCH.md) keeps every measurement, and [GATEWAY.md](GATEWAY.md) remains the path to both directions. |
| 12 | **Router importers:** eero (unofficial API, unverified against a live account) and CSV, to bring in existing device names and groups | built and wired into the portal |
| 13 | **Scheduled access and allowlist mode:** time windows on a policy rule or switch at network, group or device scope (block or allow a category, app or list only during chosen hours/days); and an allowlist mode, settable at the same three scopes, that inverts the default to block everything except what is explicitly allowed, instead of today's block-list default | built and wired into `internal/dnsengine` and the portal (docs/POLICY.md) |
| 14 | **Geo-IP blocking:** block (or alert on) connections to specific countries, at network, group or device scope, reusing the GeoIP database already used for the globe HUD | built and wired into `cmd/shepherd` and the portal (docs/GEOBLOCK.md): DNS-answer based, per scope, with the Blocking screen's Countries tab; the HUD's on-globe "block this country" control still waits on enforcement beyond DNS |
| 15 | **Network health history:** ping/latency, jitter, packet loss, bufferbloat, reachability and traceroute, run on an interval and kept over months so reliability trends are visible, not just this instant | latency/jitter/loss/reachability and a bounded bufferbloat check built and wired into `cmd/shepherd`, the alarm engine (`alarms.TypeNetworkDegraded`) and the portal (docs/NETHEALTH.md), with raw/hourly/daily rollup so history grows over months without growing without bound; latency is timed as an unprivileged TCP connect to port 53 rather than ICMP echo (no `CAP_NET_RAW`) and verified live against the real internet during development (see docs/NETHEALTH.md's "What is verified" section); both the probe and bufferbloat default off, unlike portscan/vulnscan, since this reaches fixed public internet addresses rather than only the owner's own LAN; traceroute is deferred, the same way step 16 deferred router port-forwarding discovery, for lack of a safe, verified raw-socket implementation |

| 20 | **Inbound protection:** logging, rate limits and blocking at the proxy and tunnel, exposure alarms, host-level inbound tracking | planned |
| 21 | **Mesh:** dataset sync, active-active DNS, standbys | planned |
| 22 | **Self-maintenance:** signed self-update with rollback, retention budgets, digests | built 2026-11-01. Self-update (docs/UPDATE.md): a daily check of GitHub releases, a `self-update` alarm, and "Update now" on the Overview that downloads, verifies the checksums and their Ed25519 signature, swaps the binary in keeping the previous one, restarts, and rolls back on its own if the new binary does not stay up; `-rollback` does it by hand. Releases are signed by CI once the maintainer adds the key (shepherd-sign). A read-only container cannot be updated in place and says so. Retention: `[retention] max_mb` is one budget for the data directory, split into caps for query history, bandwidth and network health, with the Overview showing use against it and a `storage-over-budget` alarm when the directory outgrows it anyway. Digest: the Notifications tab's Delivery card sets what is sent at once and when the digest goes out, over `GET`/`PUT /api/alarms/preferences` |
| 23 | **Threat feeds** (local AI set aside by decision: Shepherd stays light on the host it runs on) | threat feeds built and wired 2026-11-01 (docs/THREATS.md): four curated abuse.ch and Spamhaus feeds matched against every DNS query's name and answer, raised as `threat-match` alarms naming the device, with a Threat feeds tab on the Alarms screen; feeds from the configuration and Watch-mode destinations are not checked yet |
| 24 | **Packaging:** installers, setup wizard, release channels — including a Raspberry Pi / low-power-hardware path: Shepherd already cross-compiles to `linux/arm64` in CI, so DNS-only protection and passive ARP already run on cheap hardware people already own; Watch mode's software relay is the part that needs real headroom, not the baseline. **The stated goal here is not "easier for techies" — it's that a non-technical person should never need a terminal or a text editor at all.** Today, first setup means hand-editing `shepherd.toml` and running a binary by hand; that's acceptable for the current development phase but is explicitly *not* the bar for a real release. The portal itself should walk a new owner through setup (upstream choice, data directory, initial blocklist, locking a PIN) and keep itself running afterward (updates, retention, housekeeping) with no config file ever touched by hand — self-update (step 22) and the setup wizard here are two halves of the same promise: install it, answer a few questions in a browser, and it just works, indefinitely, for someone who has never heard of DNS. **Target hardware is deliberately broad, not just a NAS or a dedicated box**: a Raspberry Pi, a spare gaming PC, a Mac mini someone already owns — anything idle on the network. Shepherd already cross-compiles with no CGO to Linux, macOS and Windows (see the Wave 2 entry at the top of CHANGELOG.md); what's missing for each isn't the binary, it's a real installer (an .exe/.pkg/.deb or similar, not "download a binary and figure out how to run it as a service") so "easy setup" means the same thing on every platform. | **Specified 2026-11-02, not built:** [PACKAGING.md](PACKAGING.md) fixes the promise, the first-run wizard's questions, the target matrix (Raspberry Pi image, `.deb`/`.rpm`, one-line script, macOS `.pkg`, Windows `.msi`, Docker, NAS, Home Assistant) and the order of work; the wizard comes first |

## Stated future direction: Shepherd as a dual-NIC router

**Designed, not scheduled: [GATEWAY.md](GATEWAY.md)** has the architecture, the staged migration
with its rollback, the risks, the IPv6 hard rules it forces a rescope of, and the five decisions
that are the maintainer's rather than anyone else's.

The maintainer wants to eventually run Shepherd as the actual router (a "Gateway" profile), on
hardware with two 10 Gb NICs, demoting the current Wi-Fi router to a bridge/access-point role. This is
real intent, not a research idea, but it is a large undertaking that only makes sense once Watch mode
is proven reliable, and it changes Shepherd's risk profile fundamentally (a router outage is a full
outage). See [DESIGN.md](DESIGN.md#gateway-shepherd-as-a-dual-nic-router-future-stated-goal). Not scheduled.

Other research items: passive IPv6 observation, NAT state sync for seamless failover, and full
two-sided (peer) ARP isolation for quarantine/LAN-isolation beyond what one-sided Watch mode can
offer. In-path IPv6 is no longer research: unicast-NA steering is built and wired (off by default,
[IPV6-WATCH.md](IPV6-WATCH.md)), though it has never run against a live global-IPv6 network — the
maintainer's own LAN is ULA-only, so it idles there by design.
